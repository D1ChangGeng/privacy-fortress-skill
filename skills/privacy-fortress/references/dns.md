# DNS：加密、防泄漏与可恢复性

## 1. 推荐数据流

```text
应用 DNS → 平台 VPN/TUN 劫持或系统解析 → 网关 DNS
                                      ├─ 明确需要本地解析的例外
                                      └─ 加密上游（DoH/DoT/DoQ）经代理
```

目标是让目标域名的 DNS 查询路径与目标连接路径符合同一威胁模型。仅在配置里出现 DoH 不足以证明这一点：DoH 连接本身也可能 DIRECT。

## 2. DoH-over-proxy 要点

- 上游使用受信任且支持加密 DNS 的服务，记录其日志政策与可见面。
- 优先 IP 字面量端点，减少“先解析 DoH 域名才能使用 DoH”的引导循环。
- 如果必须使用域名，明确 bootstrap/default nameserver，并确保该引导路径不会泄漏目标查询。
- 对 DoH 上游的连接规则进行复核，确保不会绕过代理。Mihomo 可在版本支持时评估 `respect-rules: true`，让 nameserver 连接进入规则管线。
- 节点域名需要恢复路径时，使用受控 `proxy-server-nameserver` 或当前核心等价机制；引导 DNS 只解析必要节点/上游，避免与 fake-ip 形成回环。
- 应用硬编码的公共 DoH 也纳入规则审查，使其进入受控路径或按设计失败。
- 不使用不受控的订阅转换、公共配置生成器处理含凭据配置。

Mihomo 示例片段（仅示意，按核心版本调整）：

```yaml
dns:
  enable: true
  listen: 0.0.0.0:1053
  ipv6: false
  enhanced-mode: fake-ip
  default-nameserver:
    - <BOOTSTRAP_DNS_IP>
  nameserver:
    - https://1.1.1.1/dns-query
    - https://8.8.8.8/dns-query
tun:
  dns-hijack:
    - any:53
```

`ipv6: false` 只控制相应 DNS/核心行为，不等于操作系统 IPv6 已关闭。`fake-ip` 也需要和 TUN、过滤器、本地服务兼容性一起验收。

## 3. 本地域名例外

企业、校园、家庭内网可能需要本地 DNS 才能访问认证页和内部域。例外应：

- 只覆盖必要域名或 split-DNS 区域；
- 明确本地网络会看到这些查询；
- 不用大范围“所有国内域名直连”替代具体需求；
- 在新网络环境重新验证，防止旧假设失效。

## 4. fake-ip 兼容性

需要真实地址的功能可能需要过滤器：网络认证、某些局域网服务、快速登录、STUN、网络连通性探测。每加一项都记录原因。出现“部分网站打不开”时，先检查 DNS 核心和过滤器，不要直接关闭全部防护。

## 5. 验收

- 使用至少一个支持深度 DNS 测试的站点，观察实际递归解析器，而不只看系统 DNS 地址。
- 检查 IPv4 与 IPv6 解析器；隐藏 AAAA 不能替代 v6 出口测试。
- 检查浏览器是否另有 Secure DNS/DoH 通道。
- 更换 Wi-Fi、酒店、校园或企业网络后重测，因为中间设备可能透明拦截 UDP/53。
- 检测站无结果或请求失败记 UNKNOWN/WARN，不记 PASS。

## 6. 故障恢复顺序

1. 保持关键应用不要继续尝试敏感登录。
2. 检查唯一网关和 DNS 模块是否存活，是否存在第二个 DNS 控制器。
3. 回到最近已知良好配置；必要时关闭 TUN，恢复普通系统 DNS。
4. 验证普通网站与关键工作服务恢复。
5. 查明根因后重新小范围启用，不以长期 DIRECT 作为修复。
