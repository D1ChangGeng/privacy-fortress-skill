# 网关：单所有者、分流与故障关闭

## 1. 架构原则

```text
应用 → 平台 VPN/TUN 或系统代理 → 唯一网关 → 明确规则 → 受控出口
                                  ├─ 必要 DIRECT 例外（逐条记录）
                                  └─ 默认代理或拒绝（不得偶然直连）
```

TUN/平台 VPN 覆盖不遵守系统代理的应用；系统代理只覆盖支持它的应用。两者可同时存在，但必须由同一个网关拥有，避免回环和双重接管。

管理员或高权限进程通常能够修改防火墙、路由和 VPN 配置，因此不能宣称“管理员也无法绕过”。真正的边界是减少误操作和普通应用自行直连，不是防御已控制内核的攻击者。

## 2. 规则审查顺序

不同内核语法不同，但按以下语义审查：

1. 明确拒绝的纯遥测或不需要流量；先验证不影响功能。
2. 必须直连的本地网络、认证和关键服务；范围最小化。
3. 需要整体代理的应用/进程，包含 helper 和更新器。
4. 目标域名/IP 的代理或直连规则。
5. 私有地址、GeoSite/GeoIP 等广泛分类。
6. 最终 `MATCH`/default：代理或拒绝，不能无意中 DIRECT。

首命中内核中，最终 MATCH 后面的规则不会生效。广泛 DIRECT 规则可能抢先截走本应代理的流量，所以顺序本身必须测试。

共享运行时（如 `node`、`python`、`java`）不能只按进程名建立高信任例外，否则同机所有脚本都会继承。优先使用受控启动器、完整路径或独立用户/容器，并承认路径会随更新变化。

## 3. DIRECT 例外纪律

每条例外记录：所有者、业务用途、目标、观察者能看到什么、最近验证时间。定期清理零命中或失去所有者的条目。

- DIRECT 意味着目标服务可能看到真实公网 IP。
- 进程 DIRECT 会覆盖该进程内嵌 SDK 和浏览器组件，不只是主功能。
- GeoIP/GeoSite 是名单推断，不是安全边界；误判方向必须纳入测试。
- 局域网例外会扩大应用探测面，仅在需要时开启。

## 4. 链式代理

链式代理可以分离“入口连接”和“最终出口”的角色，但不会消除信任：

```text
本机 → 入口/中转 → 最终代理出口 → 目标服务
```

入口通常知道真实来源，最终出口通常知道目标连接，目标服务看到最终出口。供应商、协议和日志政策仍需独立评估。不要因为链式就写“无人知道真实 IP”。

UDP/QUIC 支持必须实测。如果链路不支持 UDP，可让相关流量失败并回退到 TCP，或按应用拒绝；不要静默转为直连。

## 5. 配置即事实源

- 自建核心：以版本化配置为事实源，使用官方核心校验后热加载或重启。
- GUI 客户端：先确认事实源是文件、内部数据库还是订阅；生成文件不一定是可编辑源。
- 订阅和自定义规则分离，升级前备份，升级后 diff 实际生效配置。
- 不把含节点凭据的配置、订阅链接或面板 secret 提交到公开仓库。

## 6. 静态检查与核心校验

`scripts/lint_gateway.py` 只发现高风险文本模式，不是完整 YAML 解析器，也不能证明运行时已生效。之后必须运行对应核心的官方检查，例如 Mihomo 的配置测试或 sing-box 的 `check`，再做端到端联网测试。

## 7. 部署顺序

1. 记录原网络与恢复入口。
2. 仅配置出口，保持现有路由，验证节点凭据和协议。
3. 启用一个捕获层，先测试非关键应用。
4. 加 DNS，再验 DNS。
5. 加 fail-closed，再测代理停止状态。
6. 最后扩大应用范围并做重启、网络切换和升级复核。
