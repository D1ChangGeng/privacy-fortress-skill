# Agent 工作协议：让用户知道将要发生什么

## 1. 权限分级

| 级别 | 允许动作 | 需要的确认 |
|---|---|---|
| A 离线只读 | 查看版本、路由/DNS/VPN/防火墙状态，运行离线审计，生成台账和 Plan | 用户要求审计即可；不得改设置 |
| B 在线检测 | 联系公共 IP、DNS、WebRTC 或目标服务检测端点 | 先列出端点、会暴露当前出口和测试时间，取得同意 |
| C 普通变更 | 编辑用户自有配置、生成规则、启动非特权测试 | 展示文件、命令、备份、回退和验收后逐批确认 |
| D 特权/断网风险 | 管理员防火墙、TUN、系统 DNS、服务、自启、移动 Always-on/锁死 | 单独明确确认；先准备本地恢复与必要的超时回退 |
| E 高风险非默认 | MachineGuid、系统区域/语言、远控、Root/刷机、Git 历史改写 | 不作为默认网络施工；重新评估必要性并单独授权 |

安装 Skill、运行 `--list`、读取文档、生成 Plan 都不是 C/D/E 授权。不得因为用户说过“配置好”就跳过具体变更卡片。

## 2. 标准对话流程

### 第一步：说明能力并收集最小信息

先告诉用户：本 Skill 能做只读盘点、方案设计、经确认的配置实施和双状态验收，但不能保证匿名，也不能用网页检测证明原生应用没有设备信号。

只问影响下一步的内容：

1. 设备与 OS 版本；Android/iOS 是否在本次范围。
2. 是否拥有网络和设备的修改权，是否有本地/带外恢复入口。
3. 当前 VPN/代理核心、版本、配置事实源；是否存在多个 TUN/DNS 控制器。
4. 要保护的观察者、应用和账号边界；哪些直连业务不能中断。
5. 是否允许在线检测；是否已有可用节点和本地恢复方式。

不得要求用户把订阅 URL、UUID、密码、私钥、Cookie 或 token 贴进聊天。让用户在本机受限文件中填写，Agent 只引用路径，并避免回显秘密。

### 第二步：离线只读基线

解析实际安装后的 Skill 根目录，不假设当前工作目录就是 Skill 目录。在该目录运行：

```bash
python scripts/privacy_audit.py --output ./privacy-reports
python scripts/coverage_audit.py --init ./privacy-reports/coverage.json
python scripts/coverage_audit.py --list
```

只读采集仍应最小化：不收集机器 GUID、序列号、Wi-Fi 名称、账号、完整用户目录或环境变量值。向用户展示现状、未知项和建议范围，不直接施工。

### 第三步：给出可选择的方案

方案至少包含：

- 唯一网关/VPN 所有者，TUN 与系统代理的捕获关系；
- 规则顺序、默认 MATCH、每条 DIRECT 的用途和暴露面；
- DNS 加密路径、劫持/fake-ip、引导和本地例外；
- IPv6、UDP/QUIC、WebRTC 和防火墙 fail-closed；
- 浏览器/profile 分工；Android/iOS 的平台特定步骤；
- 备份、回退、双状态验收、重启/升级复检；
- 30 项覆盖台账中哪些为 TESTED、CONFIG、UNKNOWN、RESIDUAL、NOT_APPLICABLE。

让用户选择“仅审计”“只生成配置/Plan”“逐批实施”。不要把多个架构选择藏在一句话里。

### 第四步：每批变更前展示确认卡

```text
批次：BATCH-<编号>／<名称>
目标：本批只解决什么
变更文件与精确命令：……
权限：普通 / 管理员 / ADB / 用户手动系统设置
可能影响：断网、直连、认证、更新、关键应用等
在线端点：无，或逐项列出
备份位置：……
回退命令与预计恢复时间：……
超时自愈：需要 / 不需要及理由
验收：代理在线、代理停止、DNS、IPv6、WebRTC、关键应用
请回复“确认执行 BATCH-<编号>”后才会执行。
```

未得到对应批次确认就停下。不得把后续批次视为已授权，不得在用户确认后扩大命令范围。输出可能包含秘密时先脱敏。

### 第五步：实施、回读、回退演练

1. 一次只执行一个已确认批次，先备份。
2. 写入后回读实际生效状态，不以命令退出码代替生效证据。
3. 先验证普通联网和关键工作应用，再验证隐私目标。
4. 代理在线和代理停止各测一次；需要时实际演练 Rollback。
5. 失败先恢复可用性，保留证据，再定位；不通过长期 DIRECT 或关闭锁死“修复”。

### 第六步：移动端单独确认

- Android ADB 连接、写 Always-on/锁死、改分应用清单、重启设备分别是不同授权；先回读包名、UID、旧值和恢复命令。
- iOS/iPadOS 的普通 VPN/On Demand 与 MDM Always-on 不得混称；需要用户在系统设置中操作的步骤要清楚标出。
- 不默认 Root、解锁 bootloader、刷写或安装反检测模块；缺少精确官方镜像和恢复链时停止。

### 第七步：交付覆盖报告

```bash
python scripts/coverage_audit.py \
  --ledger ./privacy-reports/coverage.json \
  --output ./privacy-reports/coverage.md \
  --require-tested
```

`--require-tested` 在仍有 CONFIG/UNKNOWN 时返回非零，这是防止误报完成的机制，不是网络故障。用户可以明确接受 RESIDUAL 或 NOT_APPLICABLE，但必须写原因。

最终答复固定包含：已实测、仅配置、未测、明确残余、变更清单、备份/回退位置、在线端点、移动端残余、下次复检触发器。不得只写“全部防护完成”。

## 3. 必须停止的情况

- 没有本地/带外恢复入口，却要求远程修改路由、DNS、防火墙或 TUN。
- 不知道当前配置事实源，或发现多个 VPN/DNS 所有者但尚未理清。
- 需要用户提供明文秘密才能继续，或日志无法避免输出秘密。
- 用户不能接受该批次的可用性影响，或回退尚未准备。
- 把检测站不可达当成通过、把配置文件存在当成运行态生效、把网页结果外推到原生应用。
